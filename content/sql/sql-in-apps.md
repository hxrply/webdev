Everything so far has been you typing SQL into a console. In an application, SQL is generated by code — which introduces the single most damaging vulnerability in web development, and a performance trap almost everyone falls into.

# SQL injection

```js
// NEVER DO THIS
const query = `SELECT * FROM users WHERE email = '${email}' AND password = '${password}'`;
```

Now suppose someone enters `' OR '1'='1` as the password:

```sql
SELECT * FROM users WHERE email = 'x' AND password = '' OR '1'='1'
```

`'1'='1'` is always true, so the query returns every user and the login succeeds as the first one — typically an admin. And it gets worse:

```text
'; DROP TABLE users; --
' UNION SELECT credit_card, cvv, 1, 1 FROM payments --
```

String concatenation means user input becomes **executable code**. This is how a large share of real data breaches happen, and it has been the number-one or number-two web vulnerability for over two decades.

# The fix: parameterised queries

```js
// ✓ Parameterised — the driver sends SQL and data separately
const user = await db.get(
  'SELECT * FROM users WHERE email = ? AND password_hash = ?',
  [email, passwordHash]
);
```

```js
// PostgreSQL (node-postgres) uses numbered placeholders
const { rows } = await pool.query(
  'SELECT id, name FROM users WHERE email = $1 AND active = $2',
  [email, true]
);

// Named parameters, in drivers that support them
db.get('SELECT * FROM users WHERE email = :email', { email });
```

The crucial point: the SQL string is **fixed** and sent to the database first; the values arrive separately and are never parsed as SQL. An input of `' OR '1'='1` is treated as a literal string to compare against — it matches no email, and that's the end of it.

:::warn Escaping is not a substitute
```js
const safe = email.replace(/'/g, "''");     // ✗ don't
```
Manual escaping fails on character-set edge cases, on numeric contexts where quotes aren't used, and on the many places you'll forget. **Never build SQL with string concatenation containing user input.** Parameterise, always, without exception — including for values you believe are safe.
:::

## What can't be parameterised

Placeholders work for **values**, not identifiers or keywords:

```js
// ✗ You cannot parameterise a column name
db.all('SELECT * FROM products ORDER BY ?', [sortColumn]);

// ✓ Validate against an allowlist instead
const ALLOWED = { name: 'name', price: 'price', stock: 'stock' };
const column = ALLOWED[sortColumn] ?? 'id';
const dir = sortDir === 'desc' ? 'DESC' : 'ASC';
db.all(`SELECT * FROM products ORDER BY ${column} ${dir}`);
```

An allowlist — a fixed map of permitted values — is the only safe pattern for dynamic identifiers. Never pass user input into that position, however filtered.

# The N+1 problem

```js
// ✗ 1 query for the list, then 1 per row = 101 queries
const posts = await db.all('SELECT * FROM posts LIMIT 100');
for (const post of posts) {
  post.author = await db.get('SELECT * FROM users WHERE id = ?', [post.author_id]);
}
```

With a 2ms round trip, that's 200ms of pure latency for data one query could have returned. It's invisible in development with 10 rows and crippling in production with 10,000.

```js
// ✓ One join
const posts = await db.all(`
  SELECT p.*, u.name AS author_name, u.avatar_url
  FROM posts p
  JOIN users u ON u.id = p.author_id
  LIMIT 100
`);

// ✓ Or two queries and a map, when a join would duplicate too much data
const posts = await db.all('SELECT * FROM posts LIMIT 100');
const ids = [...new Set(posts.map(p => p.author_id))];
const authors = await db.all(
  `SELECT * FROM users WHERE id IN (${ids.map(() => '?').join(',')})`, ids
);
const byId = new Map(authors.map(a => [a.id, a]));
posts.forEach(p => { p.author = byId.get(p.author_id); });
```

Note how the placeholder list is built from the array's *length*, not its contents — the values still go through parameters.

:::tip Count your queries
Log the number of queries per request in development. If loading one page issues 60 queries, you have an N+1 somewhere. Most ORMs have an "eager loading" option (`include`, `with`, `joinedload`) that turns the loop into a join.
:::

# Connection pooling

Opening a database connection is expensive — TCP, TLS, authentication. A **pool** keeps a set of connections open and hands them out:

```js
import pg from 'pg';

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,                       // maximum connections
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000
});

const { rows } = await pool.query('SELECT * FROM products WHERE id = $1', [id]);
```

Two things to get right:

- **Always release connections.** Use the pool's `query` method, or `try/finally` with an explicit client. A leaked connection is gone until the process restarts, and twenty leaks means a dead application.
- **Size the pool sensibly.** More connections is not better — PostgreSQL handles a few dozen active connections well and degrades beyond that. If you need more, put a pooler (PgBouncer) in front.

# ORMs and query builders

| Approach | Example | Trade-off |
|---|---|---|
| **Raw SQL** | `pg`, `better-sqlite3` | Full control, nothing hidden; more boilerplate |
| **Query builder** | Knex, Kysely | Composable, typed, still obviously SQL |
| **ORM** | Prisma, Drizzle, TypeORM, Sequelize | Fast CRUD, migrations, relations; hides the SQL |

```js
// Prisma
const posts = await prisma.post.findMany({
  where: { published: true },
  include: { author: true },       // ← eager loading, avoids N+1
  orderBy: { createdAt: 'desc' },
  take: 20
});
```

ORMs are genuinely productive for ordinary CRUD. Two cautions:

1. **Learn SQL first.** An ORM you don't understand generates queries you can't debug, and when a page is slow you'll have no idea why. You've done that work in this track — you're ahead.
2. **Expect to drop to raw SQL** for reporting queries, complex aggregations and window functions. Every good ORM provides an escape hatch. Use it rather than contorting the ORM's API.

# Handling errors

```js
try {
  await db.run(
    'INSERT INTO users (email, name) VALUES (?, ?)',
    [email, name]
  );
} catch (err) {
  if (err.code === 'SQLITE_CONSTRAINT_UNIQUE') {          // 23505 in PostgreSQL
    return { error: 'That email is already registered.' };
  }
  logger.error({ err }, 'Failed to create user');
  throw err;                       // unexpected — don't swallow it
}
```

Check the error *code*, not the message string — messages differ between versions and locales. And never return a raw database error to the client: `duplicate key value violates unique constraint "users_email_key"` tells an attacker your table and column names.

# Transactions in application code

```js
const client = await pool.connect();
try {
  await client.query('BEGIN');

  const { rows } = await client.query(
    'UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING stock',
    [qty, productId]
  );
  if (rows.length === 0) throw new Error('Insufficient stock');

  const order = await client.query(
    'INSERT INTO orders (customer_id, status) VALUES ($1, $2) RETURNING id',
    [customerId, 'pending']
  );
  await client.query(
    'INSERT INTO order_items (order_id, product_id, quantity) VALUES ($1, $2, $3)',
    [order.rows[0].id, productId, qty]
  );

  await client.query('COMMIT');
  return order.rows[0].id;

} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();                // always, whatever happened
}
```

Note the atomic stock decrement with `AND stock >= $1` — it cannot oversell even under concurrent requests, and `RETURNING` tells us whether it applied.

# Other things that matter

- **Never put credentials in code.** `process.env.DATABASE_URL`, and a `.env` file that is in `.gitignore`.
- **Least privilege.** Your application user doesn't need `DROP TABLE`. Migrations can run as a different, more privileged user.
- **Always paginate.** `SELECT * FROM events` works fine until the table has 40 million rows and it takes your API process down with it.
- **Set a statement timeout** so one pathological query can't hold a connection forever.
- **Back up, and test the restore.** A backup you've never restored is a hypothesis, not a backup.

- Too many indexes
- One query for a list, then one more per item, instead of a single join *

- A deadlock

- The error message text
- The error code *
- The stack trace
- The query string
